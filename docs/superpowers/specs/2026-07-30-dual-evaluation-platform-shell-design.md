# 双评判平台框架设计

## 背景

现有 SafeEvaluate 平台最初面向公安合作场景，已经包含登录、历史记录、统计、规则管理，以及公安派出所检查记录和责令改正通知书等定制能力。

AGULAB 官网后续需要展示一个面向更广泛用户的通用自动合规评判平台。通用平台的具体评判对象、法规输入方式和报告内容仍需进一步确认，因此第一阶段只搭建可靠的双平台框架，不提前实现未经确认的公共评判流程。

## 第一阶段目标

在同一域名下提供三个相互独立的前端入口：

- `/`：AGULAB 官网。
- `/evaluate`：通用自动合规评判平台框架。
- `/evaluate_tianxin`：现有天心区公安合作评判平台。

第一阶段必须完整保留现有天心区平台的功能和数据行为，同时为通用平台建立中性、可扩展的页面骨架和独立部署入口。

## 方案选择

采用“两个入口应用，后续逐步共享评估组件”的渐进式方案。

本阶段保留现有 `frontend` 作为天心区版本，新增 `frontend-public` 作为通用版本。暂不立即抽取共享组件，避免在产品需求尚未稳定时大规模重构现有平台。等通用评判流程确认且两个版本稳定后，再抽取上传、进度、结果展示等真正一致的组件。

未采用以下方案：

- 两套平台永久完全复制：短期简单，但长期会导致相同功能重复维护。
- 单一应用根据 URL 切换模式：代码量较少，但公共功能和公安定制功能容易相互泄漏，权限边界也不够清晰。

## 路由与应用边界

### AGULAB 官网

官网继续由 `website` 构建并服务于 `/`。官网中的评估体验入口继续指向 `/evaluate`，不公开展示天心区专属入口。

### 通用平台框架

新增 `frontend-public`，以 `/evaluate` 作为应用根路径。首期包含：

- 中性的“自动合规评判平台”名称和说明。
- 图片材料输入区域。
- 法律法规输入区域。
- 规章制度输入区域。
- 评判执行区域。
- 评判结果区域。

这些区域用于确认未来的信息架构和扩展位置。第一阶段不调用 AI 接口，执行按钮保持不可用，并明确提示“功能方案完善中”，避免形成已经提供正式评判服务的误解。

通用框架不包含：

- 登录页面和身份认证流程。
- 历史记录、统计和规则管理入口。
- 公安、派出所、天心区等定制文案。
- 公安检查记录表和责令改正通知书。
- 公共报告保存、24 小时清理或访问频率限制。

### 天心区平台

现有 `frontend` 的功能迁移到 `/evaluate_tianxin` 路径空间：

- `/evaluate_tianxin/login`
- `/evaluate_tianxin/evaluate`
- `/evaluate_tianxin/evaluate/summary`
- `/evaluate_tianxin/report/:id`
- `/evaluate_tianxin/history`
- `/evaluate_tianxin/rules`
- `/evaluate_tianxin/stats`

未登录访问天心区入口时，应用跳转到 `/evaluate_tianxin/login`。登录成功后的重定向、侧边栏链接、报告链接和安全跳转校验都必须留在该路径空间中。

现有后端 `/api/*` 接口、认证方式、数据库和文件存储在第一阶段保持不变。

## 静态资源与部署

三个 Vite 应用使用互不冲突的构建目录和静态资源前缀：

- 官网构建产物：`website/dist`
- 通用平台构建产物：`frontend-public/dist`
- 天心区平台构建产物：`frontend/dist`

Nginx 分别挂载三个构建目录，并对 `/evaluate/*` 与 `/evaluate_tianxin/*` 实施独立的 SPA 回退。刷新嵌套路由时，Nginx 必须返回对应应用的 `index.html`，不能回退到官网或另一平台。

Docker Compose 增加通用平台构建产物的只读挂载。前端构建脚本依次验证并构建官网、通用平台和天心区平台。

## 页面状态与错误处理

通用平台框架只包含本地页面状态，不产生网络评判请求：

- 输入区域可展示未来支持的材料类型，但不上传文件。
- 执行按钮使用禁用状态，并提供可读的建设中说明。
- 页面不得展示虚构的评判结果、成功状态或可用 API。

若某个平台构建产物缺失，部署检查应当失败，而不是让 Nginx 静默回退到其他应用。

天心区平台继续沿用现有的认证失效、评判失败、超时和报告错误处理，不在本阶段改变业务行为。

## 验收标准

### 路由

- `/` 显示 AGULAB 官网。
- 官网评估入口进入 `/evaluate`。
- `/evaluate` 及其刷新请求显示通用平台框架。
- `/evaluate_tianxin` 进入现有天心区平台登录流程。
- 天心区所有嵌套路由刷新后仍由天心区应用处理。
- 三个应用的静态资源均从各自路径加载，不发生文件名或缓存冲突。

### 功能边界

- 通用框架不出现公安、派出所或天心区定制内容。
- 通用框架没有登录、历史、统计和规则管理入口。
- 通用框架不发起 AI 评判请求。
- 天心区现有登录、评判、报告、历史、规则、统计和公安文书能力保持可用。
- 后端数据库结构和生产数据不发生迁移。

### 验证

- 官网单元测试、代码检查和生产构建通过。
- 通用平台单元测试和生产构建通过。
- 天心区平台现有单元测试和生产构建通过。
- Python 后端测试和编译检查通过。
- 本地集成检查覆盖三个入口、嵌套路由回退和静态资源隔离。

## 发布与回滚

发布前备份现有 Nginx 配置、Compose 配置和三个前端构建产物。部署时先完成全部构建和路由检查，再更新 Nginx 服务。

若新路由异常，恢复旧版 Nginx、Compose 和前端构建产物即可。第一阶段不修改数据库结构和后端数据，因此回滚不需要数据恢复。

## 后续阶段

待通用平台产品需求经确认后，再单独设计：

- 评判对象和输入材料范围。
- 法律法规与规章制度的输入、选择和管理方式。
- 通用提示词和报告结构。
- 公共 API、安全策略与资源成本控制。
- 临时报告保存时长和自动清理。
- 访问频率限制或其他防滥用机制。
- 两个平台之间可以稳定共享的组件和后端服务。

上述内容均不属于第一阶段实现范围。
